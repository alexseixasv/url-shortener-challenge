# ADR-003: Analytics via Redis Streams

## Context

Every valid access must produce an individual event. Analytics must not block the redirect (`302`). After the queue infrastructure accepts the event, we want recovery if the worker crashes. `LPUSH` + `BRPOP` removes the message on dequeue: a crash before the PostgreSQL commit loses an already accepted event.

## Alternatives considered

### 1. Redis List (`LPUSH` + `BRPOP`)

- Positive: minimal API; simple worker.
- Negative: at-most-once after the pop; a crash after dequeue loses an already accepted event.

### 2. Synchronous PostgreSQL outbox on the hot path

- Negative: puts analytics persistence on the redirect path; conflicts with the latency budget.

### 3. Redis Streams + consumer group + idempotency (chosen)

- `XADD` accepts the event; it stays pending until `XACK`.
- Redelivery after a crash requires deduplication on persist.

## Decision

- Queue: Redis Streams (`access_events`).
- Consumer group: `analytics-workers`.
- Each event carries an `eventId` UUID generated by the API.
- Worker: `XREADGROUP` → idempotent PostgreSQL transaction → `XACK` **only after** `COMMIT`.
- Persistence: `AccessEvent.eventId` UNIQUE; `INSERT … ON CONFLICT DO NOTHING`; aggregates (`DailyLinkStat`, unlimited `clickCount`) only if the insert created a row.
- Pending reclaim (`XAUTOCLAIM`) for dead consumers.
- Request enqueue: **best-effort / non-blocking** by default (fire-and-forget with rejection handling). Optional awaited timeout via `ANALYTICS_ENQUEUE_TIMEOUT_MS` (`0` = non-blocking).
- Poison messages: after N attempts, log + DLQ stream + `ACK` of the original.

## Consequences

### Positive

- Post-acceptance loss from a worker crash is recoverable (at-least-once + dedup).
- The redirect does not depend on publish success.
- Aligned with ADR-001 (fact + aggregates in the worker).

### Negative

- Pre-acceptance loss is still possible (Redis unavailable / process dies before `XADD` completes).
- At-least-once requires idempotency (`eventId` UNIQUE + migration).
- Worker is more complex than `BRPOP`.

## Status

Accepted.
